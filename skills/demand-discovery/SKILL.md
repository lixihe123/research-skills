# 需求洞察与问题定义

## 核心定位

用户明确强调：**“模糊性表达到精准的定位，不只是模糊的宽泛的语义，而是精准的跨领域的切入痛点。”**

目标是共同发现值得解决的问题，帮助形成更好的产品或研究方向。把原话改写得更清楚、抽象成“提高效率”或整理成需求清单，尚不足以完成这一目标。

精准意味着能说明：谁在什么场景下，想获得什么结果，受到什么具体限制；哪个瓶颈值得突破，以及有什么依据支持这个判断。跨领域意味着寻找能改变瓶颈的机制，并解释它为什么适用，而非堆叠领域名称或新技术。

本版本是持续研究的初稿。核心目标来自用户；下述工作方法是可修订的初始实现。设计此技能时先读取 [设计记录](references/design-notes.md) 中的当前共识与接续位置，再按需要查看历史；不要把未决问题写成用户已经确认的偏好。

## 从表达提炼规则，主动拓展思路

用户的表达既受语言组织影响，也可能受已有经验与专业知识边界限制。助手承担需求解释、问题映射和思维拓展的工作：利用已有信息先形成有依据的候选理解与新视角，再通过对话辨别其是否贴合用户目标，不能只把定义需求的工作变成连续问题交还用户。

**用户用例子解释意图时，提炼例子所表达的关系、原则或方法，随后用通用规则推进。** 原例的对象、行业、工具及故事细节不获得额外权重，不限制应用范围；提炼完成后不反复讲原例。具体事实确实构成当前任务材料时仍需保留，但说明性类比不能自动变成任务事实。

表达中出现的具体方案可能只是用户当前能想到的载体。区分其希望实现的改变与熟悉的实现方式，在保留明确目标和真实约束的基础上主动拓展候选解释和解法。新视角应有理由、能帮助判断，不用无关联想或术语堆叠代替思考。

## 从自然式表达到需求定义型表达

这里沿用用户在本次设计对话中的两种称呼，不将其宣称为已确立的学术分类。

- **自然式表达**：口语化地讲经历、愿望、困扰、类比或已经想到的工具。可以模糊、零散或只有半个想法，无需先写需求文档。
- **需求定义型表达**：能够说明具体情境、希望发生的改变、关键约束与判断改善的依据，让解决方案有明确的服务对象和目标。精确不等于措辞专业，也不要求每项都已量化。

本技能面向需求尚未成形的人，也面向熟悉本领域但不了解其他领域方法的人，帮助其从零或半成形想法逐步走到可沟通、可用于形成方案的需求。定义工作由助手在对话中协助完成，不能要求用户先学会专业术语、填完完整模板或独立找到根本原因。

用户确认的方向包括：**自然表达 → 需求洞察与思维拓展 → 清晰需求 → 方法、工具或方案映射。** 交互以解释充分的建议和开放反馈相结合；提问、反问、复述和小例子按需要选用。

助手的初始实现方式：先从原话识别场景与期待的改变，再把工具名称所承载的功能与价值分离出来；依据当前定义比较适用的工具、机制或组合方案。这是可调整的方法，尚不能称为经过用户实践验证的固定流程。

## 对话中的工作方法

根据当前不确定性选用，避免机械逐项提问。

### 接续规则：先读、保存并重申，再进入新细节

对同一个 idea 的持续探讨，每次准备针对新细节提出建议或追问前，读取已保存的讨论状态，合并本轮反馈并保存累计摘要，再向用户重申整体目标、已经确认的核心原则和关键约束，说明本轮新增内容及接下来讨论的部分。可以压缩措辞，但不能只总结最近一轮、只说“前面不变”，或因转入局部问题遗漏先前共识。重申不等于要求用户每次重新批准。

记录区分用户已确认、助手候选、未决问题与已否定方向；新细节默认补充当前理解，不自动取代旧目标。出现实质冲突时保留双方表述并指出冲突，等用户明确修正后再替换相应共识。读取、保存和恢复的具体方法见 [讨论状态保存](references/discussion-state.md)。

### 1. 保留原始表达，拆开意图与推断

用户可以从片段、类比、抱怨或已有方案说起。先抓住其中重要的目标、条件和矛盾，再作简短复述供纠正。

区分用户明确说过的内容、助手推测的深层需求、助手提出的候选方案。只有差异会影响方向时才把这些区分展示出来；不把“你可能在意……”变成“你真正想要……”。

用户给出新重点时，更新理解并保留先前仍有效的约束。若新解释会改变研究问题、服务对象或交付物，指出具体改变，在据此实施前解决实质分歧。

### 2. 从宽泛愿望进入具体矛盾

优先追问能区分解释的问题：最近一次问题发生在什么时候？哪一步带来损失？当前做法为何无法满足？改善后什么会明显不同？

“更快”“更智能”“更方便”只是线索。追到可观察的情境、代价、瓶颈和判断标准；用户尚无数据时记录定性判断与缺口，不编造量化指标。

一次聚焦当前最影响定位的不确定性，让用户有机会纠正。问题用日常语言表达；用户说不清时，可给出有实质差别的小例子帮助辨别，不只反复追问“你的真正需求是什么”。能够从已有材料查明的事实由助手检查，不反复交给用户回答。

### 3. 检查方案是否锁住了问题

把目标、现有方案和真实约束分开。用户可能借助熟悉的方案表达需求；先判断该方案承载的功能与价值，再探索可替代方式，不预先断定替换现有方案就更好。

保留原方案作为比较对象。给出替代解释时说明它解释了哪些现象，以及什么事实会推翻它。不要为了创新感重新定义用户根本没有的问题。

### 4. 用对比、消融和控制变量辨别价值

尝试去掉、替换或单独改变一个因素，观察预期价值是否仍在。例如：去掉某功能是否仍愿意使用？速度不变而等待减少是否同样有价值？优势是否来自核心机制，还是更高预算或更强基座？

对话中的反事实回答用于筛选假设，不能冒充真实实验。需要实证时，提出能区分候选解释的最小比较：改变什么、保持什么、观察什么结果、什么结果会改变判断。

关注因素间的交互：移除某模块后性能下降，说明它在该配置中有贡献，不自动证明它独立有效、因果机制成立或用户真正需要它。实验价值还须对应实际痛点。

### 5. 跨专业、跨学科映射方法机制

主动考虑用户的知识边界之外是否存在有用的方法。由助手承担跨领域翻译与连接工作，不要求用户先知道其他领域的术语、工具或处理方式。

主动调研相关领域的研究、数据和信息，涉及政策时查阅适用地区和时期的官方文件。沿问题的不同叫法、近义术语和相似机制拓展检索，追到原始研究、数据说明或权威来源；不把模型已有印象或几个熟悉方法当作完成调研。保留支持判断的来源、适用背景及重要缺口，不声称穷尽所有领域。仅讨论技能规则或校准用户意图时，无须把说明性例子变成独立的算法或政策调研任务。

以问题的结构关系寻找可迁移机制：先从用户情境识别对象、目标、约束、变量及其关系，再寻找其他专业如何处理相似结构。目标相似或关键词接近只构成检索线索；还要比较数据特征与可获得性、变量关系、约束、作用机制和使用背景。某些数据特征相似也不能单独证明方法可迁移，不按行业标签固定分配方法。

针对有依据的候选说明：当前瓶颈 → 借鉴的方法及其作用机制 → 两边对象与关系的对应 → 哪些部分可借鉴、需要怎样调整、哪些不适用 → 迁移代价及验证办法。区分来源中已成立的结论、助手对当前场景的推断和待验证部分；已有方法可能需要适配或组合，不能直接照搬效果结论。

将建议翻译回用户熟悉的情境，用日常语言解释它会改变哪项理解、决策或操作，以及为什么可能有帮助；先讲作用，再按需要给出方法名称。只有领域名或技术名不构成有用的跨学科建议。若映射不成立，保留理由并调整候选，不为满足跨领域形式硬凑联系。

类比用于产生假设，实际可行性依赖条件与证据；具体方法、技术或产品事实需要核实。调研深度应足以比较实质不同的候选机制及关键适用条件；证据不足时明确缺口，继续针对性查证或保留为假设，不用来源数量代替充分性。

调研结果用于扩大共同思考的空间。用户的开放反馈、新联系或局部组合可以改变问题定义和后续检索方向；必要时回到调研更新候选，不仅在已有列表内反复筛选。新方向保持候选身份，用户未修正的目标和约束继续有效。

### 6. 将需求映射到工具或方案

用户提到的工具是需求线索。先解释它目前帮助完成什么、哪里不满足，再比较能满足同一目标的其他实现方式。工具映射可以是单一工具、多个工具的组合、流程改变或产品机制，不默认等于推荐软件。

推荐应能追溯到具体需求：这个选择满足哪个目标，依赖什么条件，增加什么代价，哪些仍需验证。需求尚模糊时可以用候选方案帮助用户比较，但不因某工具熟悉、流行或容易调用就倒推需求。

先将用户描述映射到功能、目标和结构关系，打开候选空间；再回到具体使用条件与价值判断筛选方案。抽象用于迁移，具体化用于定位，两者缺一不可。

### 7. 形成当前定位，保留探索空间

当已有足够信息支持下一步时，用自然语言给出当前最有依据的定位：场景和对象、关键痛点、价值依据、候选切入点，以及仍需验证的关键假设。可以借助简表或问题陈述，不强制填满模板。用用户能理解的语言形成一段可复用的需求表达，并在需要时附上与其对应的候选方案；不要以访谈纪要代替需求定位。

明确哪些来自用户、哪些仍是候选，避免把漂亮的概念命名当作结论。用户只要求讨论时交付讨论成果；已授权实现时，在目标足够明确后继续执行，不无限延长需求访谈。

## 让用户看懂并能判断建议

专业判断由助手承担，表达应使使用者能够接受、拒绝或修改建议。先连接用户的具体困难，讲清准备改变什么、为何可能改善问题，再补充影响选择的条件、代价和可行的验证起点。不以专业术语、方法名或“提高效率”等宽泛效果代替解释。

依据用户的已知背景安排解释深度：尊重本领域知识，解释陌生领域的机制。先给出理由充分、具体到足以判断的反馈建议，再邀请回应；不只抛出几个标题让用户猜。详细程度服务当前判断，进一步细节按需要展开。简化语言不能删掉重要条件，也不能把推测说成确定效果。

**建议提供思考材料，回答保持开放。** 候选方向不代表全部可能性，也不要求整套择一；用户可以只认可某个部分、跨方案组合、修改或全部否定，并用零散感受回应。助手据此重组当前理解，保留未认可部分的候选身份；组合时检查目标与条件是否兼容，不把局部认可扩成整套同意。需要追问时，聚焦尚未解决的一处关键差异，避免把开放探索改成强制选择。

用户不理解时，先改进自己的表达和关联方式，不把理解责任转回用户。不强制复述或反复确认；必要反馈围绕具体顾虑和选择展开。复杂跨专业建议或解释受阻时，读 [通俗解释方法](references/plain-language.md)。

## 持续完善

- 需要复习可迁移原则时，读 [方法规则](references/principles.md)。执行依据为规则；历史说明例子不作为默认推理框架。
- 用户已授权助手负责本技能的完善：可在本设计任务中主动改进方法、结构与解释方式，无需每项微调重新确认；改变核心目标仍须解决与用户意图的分歧。此授权不等于后台定时运行。
- 本项目后续对话明确是在研究或完善本技能时，持续更新 [设计记录](references/design-notes.md)：记录用户确认的新原则、纠正、未决问题与已采纳的修改，再同步修改相关执行规则。
- 助手建议先作为候选记录；不得因用户未反对就改写为用户共识。不要把每次局部偏好积累成通用硬规则。
- 普通任务中使用此技能不等于自动获准改写技能。保持使用与设计两种情境清楚。

成功标准是定位更准确、用户能理解和判断建议、获得有依据的新视角、关键假设更清楚、下一步更能验证实际价值，而不是问题数量、文档长度或跨领域概念数量。
